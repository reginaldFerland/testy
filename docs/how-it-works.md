# How Testy works

This page holds the detailed behaviour behind the [README](../README.md) summary.

## How affected selection works

Testy discovers tests in isolated outputs per project and target framework, then runs selected test files concurrently in separate processes. During affected runs, projects needed only for discovery avoid coverage instrumentation; newly selected projects are prepared before execution. Source analysis overlaps runner preparation within the configured project worker budget. The scheduler uses idle project runners first and assigns spare workers to busier projects. Each worker reuses its own output and collector session; files mutated by tests are restored from that worker's pristine template before reuse. Test targets that share output directories with another framework or reference context are saved before another build can overwrite them. Testy records the workspace source files that execution reaches, including indirect calls, and keeps a separate coverage contribution for each test file. Later changes select every test file known to have exercised the changed code: for an edit inside method, accessor or constructor bodies, only the test files whose coverage executed one of the edited bodies (see [Method-level selection](#method-level-selection)).

Prepared outputs are cached between runs and can survive a clean editor shutdown. Testy validates the complete build output, preparation tools, environment, and configuration before reusing instrumentation, and runs fresh discovery on every run. Shutdown drains active work, deletes working copies and reports, and retains only pristine templates. Another editor instance can claim those templates exclusively; live instances never share mutable outputs or collector sessions. The entry allowance starts at 16 and grows to accommodate the test-file worker budget across prepared targets. Active caches and the combined retained templates each remain bounded by 512 MiB, with active work temporarily exempt. Least recently used idle entries are evicted, and outputs from crashed active owners are discarded. Custom collectors retain their complete environment, so editor environment changes can invalidate their preparations.

Learned coverage survives restarts. With each save Testy records a checkpoint: the identity the coverage was learned under (the settings that start a new baseline when changed, which are the workspace folders, build configuration, run mode, `testy.runWithCoverage`, .NET host, test arguments, exclusions, coverage tool and solution or project filters; the Testy version; the bytes of the coverage collector and runtime observer; and the environment variables, which MSBuild reads as properties, apart from launch-specific ones such as `VSCODE_*`), the test files whose saved coverage is complete, the version (content hash) and declaration shape of every tracked source file that coverage accounts for, the size and modification time of every file matching `testy.fileWatcherPattern` outside every project directory (except the non-.NET tooling files listed below), the content of each project's restored `project.assets.json`, the resolved .NET SDK versions and evaluation tools, and the changes no run has consumed yet, such as edits made while automatic testing is paused. When the workspace opens with the same identity, Testy restores the coverage of those test files as current and the startup run becomes an affected run: it still restores, evaluates, builds and discovers every project, then hashes every tracked file and treats each file whose version differs from the checkpoint, including files added or deleted while the editor was closed, as a change, and so are the unconsumed changes, the files outside every project whose size or modification time differs (including added and deleted ones, which select every test project as they do in a session), and each project whose restored assets differ, for example after a floating package version resolved to a newer package (that project and its dependents). Method-body edits select through the saved coverage like any other edit; new and deleted files and declaration changes use the conservative fallback. Test files without trusted saved coverage, such as new test files, files whose saved coverage was learned under another identity, was incomplete or stale when saved (a change had marked it and no run consumed that change), or no longer matches its own inputs, run as part of that run. A different .NET SDK, for example after a newer SDK was installed without a `global.json` pin, or different evaluation tools rerun every test file. Coverage saved under another identity, or without a checkpoint, is shown as stale history and the startup run establishes a fresh baseline; **Testy: Rebuild and Run All C# Tests** always does. A baseline interrupted by closing the editor resumes where it stopped. Other inputs Testy does not watch, such as databases, services or files outside the workspace, are not detected across restarts either; run a full refresh after them.

The coverage cache stores each path and source version once, in a shared append-only table that traces reference by position, so large solutions stay well within the 256 MiB restore limit. Records carry a format version, and the cache directory is named after it; a record of an unknown format is left untouched and ignored, and the directory of an earlier format is deleted once the current one has been restored. When most of the table is no longer referenced, a restore rewrites the cache into a fresh table. Saves write their records concurrently and publish them in order, so an interrupted save leaves every earlier record intact and the checkpoint never vouches for coverage that was not saved.

Project evaluations can also be reused within the editor session and across restarts after validating the files, existence checks, and directory searches MSBuild used. Saved evaluations are bounded to 128 project roots and 32 MiB. A full refresh or startup still checks the SDK and runs Restore before validating an existing evaluation, so generated imports and restored assets remain authoritative. Changes to imports, SDKs, file inventories, configuration, environment, or evaluation tools require fresh evaluation. Unsupported custom evaluation logic and unavailable or invalid saved evaluations use normal evaluation. Builds continue to use MSBuild's incremental checks.

Successful source analyses are retained within the editor session, including across full refreshes. Reuse requires matching source bytes, alias inputs, and analyzer context. Generated sources are checked after Build, and partial declarations and exclusions are resolved against the current projects. Incomplete analysis is retried; custom CLI wrappers or injected runtime components use fresh analysis.

The bundled collector instruments independent workspace DLLs concurrently during initial preparation when project workers are available. This shares the existing preparation budget with source analysis and discovery. Each private test-file worker still prepares one DLL at a time, and warm prepared-output cache hits skip instrumentation.

Workspace assemblies loaded from original build outputs, other paths, or memory are also recorded, including loads in child .NET processes that inherit and support the startup hook. When a load bypasses the instrumented copy, Testy records a dependency on the loaded project. Changes and new source files in that project rerun the calling test file, even without a `ProjectReference`. Those loads do not themselves supply line coverage. If runtime observation is incomplete, retained coverage stays visible and selection becomes conservative.

A collector command can succeed without instrumenting a module, for example when its symbols are missing. Testy verifies that the assembly bytes changed and retains project dependencies for skipped modules, so their callers cannot be silently omitted.

When target frameworks share an output directory, Testy snapshots each target immediately after building it. Discovery, test execution, and portable symbols use that target's copy.

New or unknown source files, project/configuration changes, missing coverage, and incomplete or failing traces use a conservative fallback: all test files in the affected project and its dependent test projects. Configuration means files that MSBuild, NuGet, the SDK or the test platform find by name (project, solution, `.props`, `.targets`, `global.json`, `nuget.config`, `packages.lock.json`, `.runsettings`, `testconfig.json`, `xunit.runner.json`, `launchSettings.json` and compiler configuration) and imports that evaluation read; only changes that can affect Restore repeat it. Other files, such as an `appsettings.json` copied to output, count as inputs of the projects that own them. A file outside every project directory that no project owns or evaluated, such as shared test data read at runtime, selects every test project without repeating Restore, since no trace can map it. Well-known non-.NET tooling files there (`package.json`, npm, pnpm and Yarn lock files, `tsconfig*.json`, `jsconfig*.json`, ESLint, Prettier, Biome, Renovate and markdownlint configuration, and `*.code-workspace`) select no tests; the default `testy.fileWatcherPattern` reports only the `.json` ones. Inside a project directory, or when a project evaluated them, they count like any other file. A Roslyn analyzer, using the compiler of the installed .NET SDK and served by a long-lived helper process, also detects declaration changes, including constants, signatures, attributes, and initializers that can affect consumers without appearing in runtime coverage. Edits in coverage-excluded methods or hidden regions also force fallback. Recorded runtime dependencies and workspace binary references are included even without a `ProjectReference`. Evaluated imports, resources and additional build inputs are tracked across consuming projects. MSBuild applies reference-specific properties when building dependencies. Ordinary method-body edits use the recorded traces, at the granularity of the edited bodies. Choose `testy.runMode: "all"` to always run the complete suite.

The first baseline requires separate test-file runs for attribution. Independent files run concurrently, including files in the same test project. Complete projects in run-all mode, and runs without collection, batch tests by project. Compatible build roots share an MSBuild invocation so their shared dependencies can be reused. Project discovery runs concurrently; files whose provider identities cannot be safely mapped to another worker use their original runner. Partial selections and exclusions also use that runner. Subsequent runs build the affected roots and execute only selected test files. See [Scheduling](#scheduling) for the order they start in. Source files with hidden or remapped `#line` regions use conservative project selection because coverage may not identify their physical methods. For unobserved external dependencies, changes to databases, services, environment variables, or data outside the watched files require a full refresh.

Changes are accumulated across cancelled runs. Completed, version-checked test files are checkpointed during the baseline, so cancellation resumes unfinished work. Each file's coverage is published as soon as it completes; contributions completing within a short window are saved together, and a cancelled run still saves what it completed. An interrupted test file never replaces its previous contribution. Instrumentation happens in temporary copies, so a cancelled collector cannot modify your normal build outputs.

## Method-level selection

The Roslyn analyzer fingerprints each executable body of a source file (method, accessor, operator and instance-constructor bodies, including expression bodies, with their lambdas and local functions) and the text around them, and reports the lines each body spans. When an edit leaves the declaration signature unchanged, the bodies of the old and new versions pair up by position, and a body whose fingerprint differs is an edited body. A test file whose coverage of the old version has no executed line in any edited body did not execute the edit, so it does not run; every other narrowing rule still applies. A typical case is a registry or dependency-injection container that constructs every handler for every test: each test's coverage reaches every handler file, but only the tests that call the edited handler method run.

The comparison is conservative. A test file runs when the layout of the version its coverage was recorded against is unknown (for example, coverage restored after a restart and not recorded against any version analyzed since), when its trace is unreliable or historical, or when an edited body has no instrumentable line, since its coverage could then not show that the body was missed. Declaration changes, files Roslyn cannot fingerprint precisely (coverage-excluded code, `#line` regions, syntax errors) and non-C# inputs keep the file-level and project fallbacks described below.

After the run, Testy moves the coverage of each test file that missed the edit to the new version of the file: body and gap fingerprints include line breaks, so lines in unchanged bodies and unchanged text between them move by the offset of their span. That coverage then stays current: it is shown fresh, saved as complete in the checkpoint, and narrows the next edit's selection. A test file whose covered lines cannot all move, for example because a comment was added next to a covered field initializer, keeps its coverage stale until it next runs.

For such edits the build is narrowed as well. When every change is a body edit of a C# source file that a project owns, Testy analyzes the edited files before building and builds every affected project except the test projects that will run none of their files: those are neither built, instrumented nor discovered. Other dependents still build, since a test can run another project's output, for example in a child process. A body edit cannot change what a dependent compiles against. A test project that was skipped is built and discovered again by the next run that selects one of its files. Should the selection after the build need a test project the narrowed build left out, the run restarts with every affected project.

Edits that only shift the lines of other bodies do not rerun the tests that executed those bodies. Code that depends on its own source line numbers, for example through `[CallerLineNumber]` or by asserting on stack-trace line numbers, can then observe different values without running again. Set `testy.selectionGranularity` to `file` to select every test file whose coverage reached an edited file. **Run Affected Tests for This File** always does so for the files it is given, changed or not.

## Scheduling

Testy learns how long each test file takes: the time from starting its test process to reading its coverage, excluding output preparation. A run only records the time when it ran the whole file, and each new time is averaged with the previous one, so a single slow run moves the estimate halfway. A batch that runs several files of a project together shares its time between them by test count. It also learns each test's own duration as the test framework reports it, averaged the same way. Times are saved with the test outcomes, so they survive a reload. **Reset Caches and Baseline** forgets them.

The order depends on what the run is for:

- **Affected and manual runs favour responsiveness.** Files whose latest results include a failure start first, then files with no learned time (usually new ones), then the shortest files. The likeliest failures report soonest.
- **Baselines, `testy.runMode: "all"` and manual runs of every test favour throughput.** The longest files start first, so no long file is left running alone at the end. A file without a learned time counts as the average. With more than one test-file worker, one worker takes files from the short end of the queue, so results still arrive early. During a baseline, files that pending edits keep invalidating still go last.

Workers prefer idle test projects first, as before, because another worker on a busy project needs its own prepared output. Between equally busy projects, the file that comes first in this order starts first.

### Long files

A throughput run on several workers can still end with one long file running alone. With `testy.splitLongTestFiles` (on by default), a file whose learned time is at least two seconds and at least each worker's share of the whole run is split into parts: its tests are dealt, longest first by their own durations, to the part with the least expected time, up to one part per worker. The parts run like separate files on separate workers, each in its own test process, and the file commits once every part has finished: their results, their coverage summed, their dependencies combined, as one complete run of the file. If a part fails to run, the file's results stand but its earlier coverage is kept. Files with shared-resource traits, excluded tests or runtime-only rows are not split. A file's tests then do not share one process; turn the setting off for test classes that rely on that.

### Per-test time limit

`testy.testTimeoutSeconds` (120 by default) limits each test, counted from the moment the framework reports the test as in progress. A test that runs longer stops its test process (the reused host as well), and the test and any others of its batch without a result are reported as errored, naming the test and the limit; the other batches continue. Frameworks that report no in-progress updates are limited only by `testy.timeoutSeconds`, which bounds a whole test-file run. Debug runs have no limit.

### Process priority

Builds, coverage instrumentation and test processes start below normal priority (`testy.processPriority`), and their descendants inherit it: a POSIX nice value of 10, or Windows' below-normal priority class. A run that keeps every CPU busy then leaves the editor responsive. Choose `normal` for timing-sensitive tests. The MSBuild server keeps the priority of the build that started it.

### Superseded runs

A change during an automatic run does not throw away the test files it is running. Once the run is testing, the change supersedes it: no further file starts and the running files finish, within `testy.finishRunningTests` seconds (5 by default; `0` cancels at once, as before). When the change is known to affect every running file (their own files, files their last coverage reached, or any non-C# change), the run stops at once instead. A finished file commits only if every source version its coverage depends on is still the one it ran against. The run then ends as cancelled, so its changes stay pending, and the next run starts with them and the new change. Files that committed in the superseded run are selected again only by what changed since they ran: a file the new change does not select keeps its results and its coverage, which becomes current. Changes before testing starts still cancel the run at once, as do full refreshes, manual runs and pausing.

### Pinned and failing files

**Pin to Automatic Runs** on a Test Explorer test, class, file or project adds it to every automatic run, whatever the changes select; pinned items are remembered per workspace and listed by the `testy.pinned` context key, so the item's menu offers **Unpin from Automatic Runs**. A pinned test of a file the changes already selected joins that file's tests, narrowed or not. With `testy.alwaysRunFailing`, every file whose latest results include a failure also runs with each automatic run until it passes. Both show as the reason in **Why Was This Selected?** and the run output. Continuous runs keep to their own scope.

While tests run, the status bar shows the time left once any selected file has a learned time, for example `Testing 12/40 · 9 active · about 35s left`. The estimate adds the expected times of queued files and the remaining times of running ones, and divides by the number of workers.

### Timeline and slow files

**Testy: Export Timeline…** writes what Testy did in the last 10 minutes as a [Trace Event Format](https://docs.google.com/document/d/1CvAClvFfyA5R-PhYUmn5OOQtYMH4h6I0nSsKchNAySU) file that [Perfetto](https://ui.perfetto.dev) and `chrome://tracing` open, like NCrunch's timeline report. The `Engine` lane holds each run (named by kind, with its change count and whether it was cancelled or superseded), its phases (the same as the `Testy timing:` lines in Output) and source analysis, which overlaps test preparation. `Preparation` lanes hold each MSBuild invocation, each test target's discovery and each assembly's coverage instrumentation, on as many lanes as overlap. Each test-file worker has its own lane: a span per test batch, from requesting a runner to committing its results (with its test and failure counts; `chrome://tracing` colours passing batches green and failing ones red), and inside it the test process itself. `Waiting` spans on a worker lane mark where it was idle while files were still queued, waiting for a shared resource (see `testy.exclusiveTraits`) or a busy test project. An `Event-loop delay` counter shows how late the editor's extension host ran its timers during runs, in milliseconds. At most 20,000 spans and samples are kept.

**Testy: Show Slowest Test Files and Tests** lists the test files with the longest learned run times and the tests with the longest durations (see above), longest first.

### Queue and line costs

The **Testy Queue** view lists the batches of the current or latest run with their state: running (with the time so far and the expected time), queued (in the order they may start, with the expected time), then failed, passed and stopped ones, each with why it was selected and, for a split file, which part it is. It is the counterpart of NCrunch's processing queue.

The covering hover of an inline result adds what the tests through the line cost. When every covering file has each test's own coverage (see [Test granularity](#test-granularity)), these are the tests whose coverage ran the line, with their own durations; otherwise they are the covering files with their learned times. It shows the total and the slowest. NCrunch measures the time spent on each line with its own instrumentation; Microsoft's collector records hits but no times, so Testy reports the cost of the tests through a line instead.

### Coverage suppression

Like NCrunch's `//ncrunch: no coverage`, a `// testy: no coverage` comment on the line before a method, constructor, property, indexer, operator or type leaves it uninstrumented, and `// testy: no coverage start` … `// testy: no coverage end` does so for every member that starts between them (a region without an end runs to the end of the file). Lambdas and local functions inside a suppressed method are left out with it. Before instrumenting, Testy looks for the marker in the tracked C# sources (rereading only files whose version changed), asks the analyzer for the members it covers, and passes the collector a settings file that excludes their functions (`dotnet-coverage instrument --settings`); the patterns are part of every prepared output's identity, so cached outputs follow them. Output says how many patterns apply. Suppressed code shows no coverage, so an edit anywhere in a file that contains the marker selects conservatively, as for `[ExcludeFromCodeCoverage]`, which works the same way per method or class.

NCrunch recommends suppression for heavily executed code, since its instrumentation slows such loops considerably. Microsoft's collector adds little there: a 400-million-iteration loop took about 433 ms instrumented against about 690 ms uninstrumented in the same Debug build (three runs each; the instrumented copy was not slower). Suppression is still useful for code whose coverage is noise, such as diagnostics helpers.

## Safety net

Impact detection can miss a test, for example one that reaches changed code through reflection, a database or a service Testy does not observe. With `testy.safetyNet` set to `related` or `all`, each automatic affected run queues the test files it did not select: with `related`, the other files of the test projects the changes affect (the files the conservative project fallback would run); with `all`, every other test file. Once the editor has been quiet for two seconds, with nothing pending, running or waiting, Testy runs them with automatic-run rules: excluded traits stay out, and pending changes are not consumed. Any change, manual run or pause cancels the safety-net run like an automatic run. The files it did not finish stay queued and run in the next quiet period. A file that ran in a later automatic run is no longer queued.

A queued file that fails although its latest results passed is reported in Output, with a notification: a change broke it, but selection did not choose it. If that repeats for the same kind of edit, `testy.selectionGranularity: "file"` or a trait-based exclusion may suit those tests better. In `testy.runMode: "all"`, and after a baseline, every file already ran, so nothing is queued.

## Test granularity

With `testy.selectionGranularity` set to `test`, Testy learns the coverage of each test, not only of each test file. When a test file runs in a run that edits started, its tests run one request at a time in the file's test process, and after each one the collector writes a snapshot of the coverage since the previous one and resets it (`dotnet-coverage snapshot --reset`, about 47 ms on an Apple M5, mostly the collector's own start-up; its command-line client is the only snapshot interface, so Testy runs it directly rather than under its process owner, which saved about a third). The file's coverage is the sum of its tests' coverage, so everything else (coverage display, file-level selection, restarts) works as before. Learning is lazy: a baseline or a run of everything takes no snapshot per test, except to keep the coverage of files that already have it current, so the first edit that selects a file runs it whole and learns its tests' coverage, and later edits narrow it.

When an edit selects a file by its coverage, Testy then narrows it to the tests whose own coverage executed an edited body, using the same body comparison as [method-level selection](#method-level-selection). For example, an edit of one handler reruns only the tests of a shared handler test file that call it. The narrowing is conservative, and the file runs whole when:

- a test has no coverage of its own yet,
- the file depends on a change only through runtime observation or build inputs,
- a change is a declaration change, a non-C# file or a file Roslyn cannot fingerprint precisely,
- or every test is affected anyway.

After a narrowed run, the coverage of the tests that did not run moves to the new version of the edited file, as for unaffected files, and together with the new coverage of the tests that ran it replaces the file's coverage, which stays current. If a test's coverage cannot move, for example because a comment was added next to a line it covered, the file keeps its stale coverage and its next run is complete. Per-test coverage is kept for the editor session only: after a reload, a file narrows by test again once it has run completely.

Two costs come with it. Every complete run of a file in an affected run takes one snapshot per test. And tests in one process share state: a value an earlier test cached or a singleton it created lazily appears only in that test's coverage, so an edit of the code that created it reruns only that test, not the later ones that used the cached value. NCrunch has the same limitation. Set `testy.safetyNet` to `related` to run the rest of such files in the background once the editor is quiet.

## Reused test hosts

A new test process costs the host's start-up (about 400 ms with the collector on an Apple M5) for every file. With `testy.reuseTestHosts` (on by default), each test-file worker keeps one test host per test project for the whole run and sends each file to it as a new MTP run request. A collector snapshot after each file splits the coverage between files, so every file keeps its own coverage. Measured on the ImpactDemo fixture, the second file in a host took 72 ms instead of 364 ms; a baseline of 120 files took about a third less time, and a run of everything less than half (see the [performance review](performance-review.md#reused-test-hosts)).

When a run completes, its test hosts, prepared outputs and discoveries are kept for the next run. That run reuses them when every build output they were prepared from is byte for byte unchanged and nothing else they were prepared under changed (settings, coverage tool, project graph): for example a safety-net run, or a manual rerun with no edits in between. Otherwise they are released before the run prepares new ones. Kept hosts end after ten idle minutes, with a cancelled run, and when Testy stops. Output says when a run reused them.

A file whose tests have a trait listed in `testy.isolatedTraits` runs in a test process of its own: a reused host of its output ends first, since the output is restored for it. With `testy.testProcessMemoryLimit` (MiB), a reused host whose process tree, with its collector, uses more after a file is replaced by a new one for the next file; the memory is read with `ps` on macOS and Linux and through CIM on Windows.

Files sharing a process see each other's effects. Static state, loaded assemblies, environment changes and files written into the test output persist from earlier files, and the output is restored from its pristine template only when a new host starts. A static constructor runs once per process, so its coverage belongs to the first file that triggers it: edits of static constructors and field initializers already fall back to the whole project (see [Method-level selection](#method-level-selection)), but lazily initialized values have the limitation described under [Test granularity](#test-granularity). Assemblies loaded at runtime are attributed to every later file of the host, which only widens selection. A file that fails the host (a crash, a timeout, a cancelled run) stops it, and the next file starts a new one. Debug runs always start a new process. Turn the setting off, or list their traits in `testy.isolatedTraits`, for tests that need a fresh process.

## Excluded traits

`testy.excludeTraits` lists test traits that automatic runs leave out: `Key=Value` matches that trait, and a bare value matches a category trait (MSTest `TestCategory`, NUnit `Category`, an xUnit `Category` trait) of that value, both ignoring case. Excluded tests are still discovered and shown in Test Explorer, and run when you select them yourself, but automatic and baseline runs never run them: a test file runs without them, and a file with only excluded tests does not run at all. A file's coverage then describes its remaining tests, so a change that only excluded tests execute selects nothing. Files that contain excluded tests run on their project's primary runner rather than a parallel worker. Changing the setting starts a new baseline.

## Coverage and results

Fresh coverage is published to Test Explorer's native coverage view, where it can be filtered by test file or project. Method (function) coverage comes from the method spans in the collector's Cobertura report: lambdas and local functions count toward their enclosing member, and async or iterator methods are reported under their own names. Statement ranges follow the open editor's text when the file is open. With `testy.showCoverage` enabled, gutter markers also appear:

- A **filled green circle** marks a covered line.
- A **red ring** marks an uncovered line.
- An **amber diamond** marks coverage that is stale or belongs to an unsaved version of the file.

Rerunning a file replaces its coverage contribution while retaining contributions from other tests. Deleted tests lose their contributions. Coverage from different versions of a source file is never combined into a misleading green result. A manually selected subset of a test file does not overwrite that file's complete coverage contribution. Manual runs without collection preserve the existing impact map. Editing a contributing test or dependency marks retained production coverage stale, even if the production file itself is unchanged.

A manual subset of files in run-all mode collects separate file contributions. The previous project aggregate remains visible as stale history until every file has been relearned or the whole project runs again. The same retention applies when switching from run-all to affected mode. Outcomes for tests outside the final affected selection remain available.

Some frameworks report deferred theory rows under one shared test identity; Testy preserves a failure if another row subsequently passes. Testy maps runtime-only rows using provider identities, source paths, and unambiguous type/method metadata. If a row cannot be selected individually after discovery, Testy runs its containing file. Rows whose file cannot be identified appear under **Unmapped runtime tests** and rerun their project. Output explains the expanded selection.

Explicit exclusions still apply to that fallback. If a runtime-only exclusion cannot be honored by the provider, the run reports the limitation before executing tests. An unavailable coverage cache is reported in Output and does not prevent a fresh startup baseline.

A manual test selection preserves failures from unselected runtime rows. Their outcomes change only when those rows run again or a complete run establishes that they no longer exist.

Overlapping manual selections run each discovered test once after fallback expansion. A complete refresh removes runtime rows that no longer exist, including when the project runs file by file or resumes from a completed checkpoint. Partial or cancelled refreshes retain unresolved rows until the remaining project files finish.

Test failures include their messages and stack traces in Test Explorer. Each test's output is attached when its result arrives. MTP's server protocol delivers standard output and error only with a test's final result (verified with MSTest 4.3.3 and xUnit v3 3.2.0), so output cannot be streamed while a test is still running. The status item shows progress, passing/failing totals, and fresh production-code line coverage. **Testy: Show Output** includes build output and explains each selection. Each test's latest outcome is saved with the coverage cache, so after a reload the status item shows the previous totals and previously failing files still run first. Outcomes of tests that a complete run or a rediscovery no longer reports, and of removed test files, are dropped. **Reset Caches and Baseline** deletes saved outcomes; **Clear Coverage** only hides coverage.

## Concurrency, generated files and watched inputs

Builds run with the MSBuild server (`DOTNET_CLI_USE_MSBUILD_SERVER=1`), which keeps MSBuild's entry node alive between builds the way the compiler server already is, so each save skips its start-up. A value of `DOTNET_CLI_USE_MSBUILD_SERVER` in the environment is respected; set it to `0` to turn the server off. In the `save` trigger mode, runs start 50 ms after the latest save unless `testy.debounceTime` is set; in `fileSystem` mode the default is 500 ms, since one operation such as a branch switch writes many files. A later change always restarts the wait and cancels an automatic run in progress.

Concurrency settings use `0` for automatic. Test-file workers use `max(1, available CPUs - 1)`; initial project preparation uses `max(1, min(4, available CPUs - 1))` because builds and source analysis can also schedule internal parallel work. For example, a machine with 10 available CPUs uses 4 project workers and 9 test-file workers. Each additional file worker can prepare its own isolated runner and consumes additional memory. Use `1` for sequential operation or an explicit positive integer to choose either limit. These settings apply on the next run without clearing learned coverage. Test frameworks retain their own internal scheduling. Private outputs isolate files in the build output, not external resources such as databases or fixed ports. To keep only the files that share such a resource apart, name it with a trait and list it in `testy.exclusiveTraits`: two test files whose tests match the same entry never run at the same time, while other files keep running in parallel. Files that may share the resource with each other, such as tests that only read a database, list it in `testy.inclusiveTraits`: they run side by side, but never beside a file that uses it exclusively. Test files that use several CPUs themselves take more than one test-file worker with `testy.workerTraits`, for example `{ "Category=Parallel": 4 }`, so fewer other files run beside them. A file waiting for a resource does not hold up later files. Test files whose tests match `testy.serialTraits` wait until no other test file runs, and nothing starts beside them. Both match traits like `testy.excludeTraits`, and since a file runs in one test process, a trait on one test applies to its whole file. Parallelism inside a test process is up to the test framework. `testy.maxParallelTestFiles: 1` still runs every file sequentially. Output reports the resolved limits, phase timings, and any identity or build-output constraints on parallelism.

Generated files, build outputs and editor state (`bin`, `obj`, `TestResults`, `.vscode`, `.vs`, `.idea`, `*.g.cs`, `*.generated.cs`, `*.designer.cs`, and files with an auto-generated header in the first 2,048 bytes) do not trigger test runs. Observed generated headers remain recognized through deletion and rename; a refresh or save that sees ordinary content clears that classification. Header-marked outputs and configured `testy.exclude` patterns are also excluded from input hashes, so a generator that rewrites them during a build does not restart the baseline. Ignored Compile inputs still supply global aliases and partial-type coverage-exclusion metadata for conservative source analysis. Evaluated generator inputs remain tracked unless explicitly excluded. Directory events honor the same exclusions as their children. VS Code file renames and deletions are handled in both trigger modes.

Generated headers must be declarations in leading comments. A marker such as `"<auto-generated/>"` inside a handwritten test or an explanatory comment does not exclude that file. Inherited `.editorconfig` files, global analyzer configuration, and configured rulesets are tracked as compiler inputs. Creating or deleting a previously absent configuration also invalidates the consuming projects, including changes that arrive while tests run.

Saved and on-disk generated headers use the same 2,048-byte prefix, including UTF-8 and UTF-16 files with a BOM in either byte order. Removing a generated header makes the file an ordinary tracked input again.

Filesystem mode also watches evaluated source files and build inputs linked from outside the workspace, including known inputs outside the usual file-pattern extensions. In that mode, an incremental run reads only the files the watchers reported; the first run after startup, full refreshes, project changes, manual runs and save-triggered runs check every known input, so edits made outside the editor are still found. After an incremental run, every known input is checked in the background, and changes found without a file event (for example, a dropped event or a folder in `files.watcherExclude`) start a follow-up run; a starting run stops that check, so it never delays the run. Overlapping watchers can report one change more than once; such reports coalesce into one run. An input that changes unreported is detected after the next build that uses it, which restarts the run with that change. Excluding a referenced project from discovery does not prevent MSBuild from building that required dependency.

External input watchers are installed before builds and discovery, allowing a corrected linked file to recover a failed run. Inherited `global.json` candidates are tracked before SDK validation, so correcting an invalid initial SDK pin also triggers recovery. SDK file creation and deletion participate in input-version checks.

## Boundaries

- VS Code 1.140 or later, with a trusted local workspace or a remote extension host that has the .NET CLI.
- .NET SDK 10 or later; test projects must target .NET 10 or later and enable MTP. Referenced production libraries may target compatible earlier frameworks.
- An MTP test framework that supports the standard discovery and execution server protocol. Integration tests cover MSTest 4.3.3, xUnit v3 3.2.0 with MTP v2, and NUnit 4.4.0 with adapter 6.3.0.
- Portable debug symbols for source mapping and coverage. A missing source location causes conservative selection.

The Test Explorer tree is filled eagerly rather than when a node is expanded. Affected selection must know every test project's tests and their source files before it can map a change to them, and discovery needs a build and an MTP discovery request per project. Discovering only on expansion would save no work and would leave tests in collapsed projects unselectable.

Test discovery is scoped to projects inside the opened workspace folders. Referenced projects outside those folders are built as dependencies, but their tests are not discovered. A build failure stops the current batch, including independent projects.

When an evaluated project stops being a test target or leaves the workspace, its test inventory, runtime rows, coverage and baseline checkpoints are removed. Required references still build as dependencies. These removals persist even if a subsequent build fails.

Source analysis can inspect generated declarations only when they appear in evaluated Compile inputs. If a source generator applies coverage-exclusion metadata through compiler-only output, use `testy.runMode: "all"`. Changes to external services, environment variables, and unwatched data require a full refresh.

Child execution that suppresses startup hooks or runs through an external service cannot supply module dependencies. Use run-all mode when tests rely on workspace code executed that way.

Testy cleans up owned test processes after completion, cancellation, and extension-host failure. On Windows, a Job Object contains descendants. On macOS and Linux, an independent supervisor watches the extension host’s control pipe and combines process groups with an inherited ownership marker to find detached children. The supervisor uses VS Code’s bundled runtime; no separate Node installation is required. Programs that deliberately remove that marker and detach, or launch work through an external service, must manage that work's lifetime themselves.

Private run output carries process ownership metadata. Startup and subsequent runs reclaim output left by dead hosts while preserving live windows' output. Unmarked directories created by older versions are preserved because their ownership cannot be verified.

Testy does not migrate VSTest projects or edit their package references. VSTest test projects and test targets older than .NET 10 are skipped and listed in Output; the run fails with an actionable setup error only when no supported test target remains. If your workspace uses a `global.json`, it must select a supported SDK. Microsoft documents [MTP setup](https://learn.microsoft.com/en-us/dotnet/core/testing/microsoft-testing-platform-intro) and the [.NET 10 CLI integration](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-test-mtp).
